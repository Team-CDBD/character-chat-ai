1 · 전체 구성

BE와 AI는 두 종류의 계약으로만 연결됩니다

AI는 BE의 DB를 읽지 않고, BE는 AI의 프롬프트나 벡터 저장 방식을 모릅니다. BE는 생성 요청(POST /generations)과 Lifecycle 이벤트(POST /lifecycle-events) 두 가지만 보내고, 답변은 SSE로 받습니다. 접수와 실행은 분리되어 있어서 ai-api는 DB에 저장하고 202로 답할 뿐 요청 안에서 모델을 부르지 않습니다.

제품 BEai-apiLifecycle 루프 생성 슬롯기억 슬롯AI DB모델 Provider

생성 경로 (Hot path) · 빠르게

BE의 생성 요청 → 입력 정리 → 기억 검색 → Context 고정(스냅샷) → 모델 1회 호출 → 문장 단위 정책 검사 후 스트리밍. 실패하면 명확한 오류 코드로 끝나고 재시도는 BE가 정합니다.

기억 경로 (Cold path) · 정확하게

BE의 AnswerCommitted → Pre-filter → 경량 모델 구조화 추출 → 근거 검증 → Reducer → 임베딩 → 요약. 확정된 답변만 기억하고, 원본 Turn이 남아 있어 언제든 다시 처리할 수 있습니다.

4 · 인터랙티브 플로우

버튼으로 따라가는 서버별 처리

빛나는 버튼만 누를 수 있습니다. 누르면 오른쪽에 그 서버가 하는 일, 담당 코드, 입출력 데이터와 정제 예시가 나오고, 그다음에 이어지는 단계만 켜집니다. 병렬로 갈라지는 곳은 여러 버튼이 함께 켜지고, 선택지(예: 후보 답변 이후 행동)는 하나를 고르면 나머지가 꺼집니다. 지나간 단계(점선)는 다시 눌러 내용을 볼 수 있습니다. 예시 데이터는 골든 시나리오(Day 1 "다음 주 금요일에 면접 있어" → Day 7 "좋은 아침")입니다.

6 · BE 연동 가이드

BE가 만들어야 하는 것

계약의 원본은 ai-service/app/api/schemas.py이고 ai-service/contracts/(OpenAPI · JSON Schema · fixture)가 여기서 자동 생성됩니다. BE는 이 디렉터리를 기준으로 클라이언트를 만들고 fixture로 계약 테스트를 하면 됩니다.

6-1. Lifecycle 이벤트 발행 (Outbox)

이벤트BE가 보내는 시점집계 · seqpayload 핵심AI에서 일어나는 일
ConversationOpened대화를 처음 만들 때 (생성 요청보다 먼저)CONVERSATION / conversationId, 1epoch, characterRevision + character 전체, personaRevision + persona, openingScene대화 등록, 설정 사본, Turn 0, 관계 기본값, BASELINE
AnswerCommitted사용자가 다음 메시지를 보내 직전 후보가 확정될 때CONVERSATION, +1turnSeq, characterRevision, userMessage{id,text,sentAt}, assistantMessage{id,responseId,text}확정 Turn 저장, MEMORY Job
CharacterRevisionChanged캐릭터 카드 또는 Persona 수정 시, 그 캐릭터의 대화마다CONVERSATION, +1새 revision 두 개 + 카드 · Persona 전체 사본새 사본, 다음 신규 Turn부터 적용
ConversationReset대화 초기화CONVERSATION, +1oldEpoch, newEpoch (= old + 1)옛 epoch 차단·정리, 같은 설정으로 새 epoch
CharacterDeleted캐릭터 삭제CHARACTER / characterId, 1부터characterId, conversationIds[]모든 대화·세대·설정 사본 삭제, 차단표식
  • 순번: 집계(aggregateType, aggregateId)마다 1부터 빈틈없이 증가해야 합니다. 빈 번호가 있으면 뒤 이벤트는 RECEIVED로 계속 보류됩니다.
  • 재전송: 실패하면 같은 eventId로 다시 보내면 됩니다. 같은 eventId는 같은 receiptId를 돌려주고, 같은 seq가 다른 eventId로 오면 중복으로 처리됩니다.
  • 202 ≠ 반영: 초기화·삭제처럼 완료를 알아야 하는 이벤트는 GET /lifecycle-events/{receiptId}로 APPLIED를 확인합니다. FAILED는 원인을 고쳐 같은 seq로 다시 보내야 그 대화가 풀립니다.
  • 봉투 필드: schemaVersion "1.0", eventId, tenantId, ownerId, aggregateType, aggregateId, aggregateSeq, occurredAt, type, payload. 알 수 없는 필드는 422입니다.

6-4. 연동 순서 제안

  1. 계약 고정: contracts/schemas로 BE 쪽 타입 생성, contracts/fixtures를 BE 계약 테스트에 넣기.
  2. 로컬 연결: docker compose -f ai-service/infra/docker-compose.yml up으로 AI를 띄우고 ConversationOpened → 생성 → SSE 중계까지. 빠른 반복에는 AI_PROVIDER=mock, 실제 답을 보려면 Ollama 모델을 먼저 pull.
  3. Outbox: 대화 생성·메시지 확정·설정 수정 트랜잭션에 Outbox 행을 넣고 발행기(재전송, eventId 유지) 구현.
  4. 후보와 확정: completed를 후보로 저장하고, 다음 메시지 때 선택된 후보로 AnswerCommitted 발행 → requiredLifecycleSeq 연결.
  5. Regenerate · Retry: contextSnapshotId 보관, retryable 힌트로 재시도 정책.
  6. 초기화 · 삭제: BE에서 즉시 차단 → 이벤트 발행 → receipt APPLIED 추적.
  7. 운영 값: 서비스 토큰 비밀값, 내부망 전용 노출, SSE 프록시 timeout(keepalive 15초보다 길게), 사용자 일일 토큰 한도.
  8. 모델 공급자 (AI 쪽): AI_PROVIDER를 ollama · openai · mock 중에서 바꿔도 같은 계약으로 동작합니다. BE 변경 없음. Ollama는 응답이 느릴 수 있어 deadlineAt을 넉넉히 잡아야 하고, OpenAI는 대화 내용이 외부로 전송되고 요금이 발생합니다.

6-5. BE와 합의가 필요한 임시 가정

#지금 코드가 가정한 것합의되지 않으면 영향
1대화 이벤트는 CONVERSATION/{conversationId}, 캐릭터 삭제는 CHARACTER/{characterId}로 각자 aggregateSeq를 1부터 셈순번이 다르게 매겨지면 Inbox가 gap으로 보고 멈춤
2CharacterRevisionChanged는 대화 단위로 발행, 카드·Persona 전체 사본 포함. Persona 변경도 같은 이벤트캐릭터 단위로만 오면 대화별 revision이 갱신되지 않아 CONTEXT_NOT_READY
3첫 장면은 ConversationOpened.openingScene으로 받고, 초기화 때는 ConversationReset(old, new)만 보내면 AI가 기존 설정·첫 장면으로 새 epoch를 엶BE가 초기화 후 Opened를 따로 보내면 중복 처리 규칙을 다시 정해야 함
4오류 코드와 retryable 힌트는 6-3 표를 따르고 최종 Retry 판단은 BEBE가 retryable=false를 재시도하면 같은 실패 반복
5사용자 일일 토큰 한도는 BE 원장 소유. AI는 usage_ledger에 용도별 사용량만 기록한도 검사가 어디에도 없게 됨
계약에 아직 없는 것: 생성 취소 API(구독 종료는 취소가 아님), 기억 조회·편집 API(MVP 범위 밖), 사용량 조회 API. 필요하면 v1에 추가하거나 v2로 엽니다.
이 문서의 기준: main(Ollama 기본 공급자까지)에 아직 머지 전인 PR #5(FAILED 이벤트 본문 보존, 임베딩 실패 비치명화, subject 정규화, Inbox 인덱스)와 PR #9(충돌 기억만 숨김, 정확한 토큰 수, 임베딩 재색인, 튜닝 값 ai-service/docs/tuning.md, Docker 빌드 검증)를 더한 상태입니다. 계약 형식은 바뀌지 않았고, BE가 알아야 할 변경은 NEW + contextSnapshotId가 422라는 점과 FAILED 영수증 본문이 남는다는 점입니다.
남은 주의점 (PR #9에서 문서화만 함): ① 임베딩 버전은 모델 이름으로만 구분해서, 같은 이름으로 모델 내용이 바뀌면 재색인이 안 됩니다(태그를 바꿔야 함). ② 배포 중 워커마다 AI_EMBEDDING_MODEL이 다르면 서로의 벡터를 번갈아 다시 만듭니다. ③ 캐릭터 카드를 고칠 때마다 활성 대화당 기억 40개당 모델 1회 호출 비용이 들고, 기억 처리가 잠시 밀릴 수 있습니다.

AI DB 테이블 관계

모든 대화 단위 테이블은 tenant_id · owner_id · conversation_id · epoch를 갖고, 모든 조회·쓰기가 이 범위로 걸립니다. BE 테이블과는 조인하지 않습니다.
